# Release v0.4.0

Org-default model correctness on custom release namespaces
([ISI-7354](/ISI/issues/ISI-7354)), plus everything merged to `main` since
`v0.3.0` (39 commits).

## Why

PR #1013 / `db7e9d76`: the compose `/api/modelconfig` write
(`mcKey()`) and the model-endpoint surfaces hardcoded the namespace
`k8squad-system`, while the chart seeds the resolver's `default`
ModelConfig singleton in the RELEASE namespace. On any install with a custom
release namespace, Console Settings saves of the org-default model never
reached the seeded singleton — and on a cluster hosting several installs, the
save mutated the OTHER install's org default (live cross-install incident on
k8squad-test during WS-4, ISI-7267). The fix targets the release namespace for
the org-default ModelConfig singleton, moves modelconfig RBAC into a
namespaced `<release>-apiserver-modelconfig` Role (the apiserver ClusterRole
no longer carries modelconfigs), and rides inherit-tier `effective-model`
reads on a direct reader instead of the informer cache (kills the >25s hang).

## What ships

- Git tag `v0.4.0` on `main` → `build-images.yml` semver lane publishes
  `ghcr.io/k8squad/ksquad-<component>:0.4.0` (cosign signatures + SLSA
  provenance).
- Control-plane chart (`config/helm`) `version`/`appVersion` → `0.4.0`.
  The default image tag falls back to `.Chart.AppVersion`, so an unpinned
  public install resolves `:0.4.0` images.
- CRDs chart unchanged (`0.3.0`): the CRD diff
  `v0.3.0..main -- config/crd/bases/ config/helm-crds/` is empty, so
  `k8squad.io/min-crds-version` stays `0.3.0`.
