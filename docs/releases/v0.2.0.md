# Release v0.2.0

First pinnable K8squad release. Before this, the project had **no git tags** and the
Helm charts were frozen at `0.1.0` since 2026-09-01 while CI published only mutable
`main` / `sha-<commit>` image tags. Combined with `pullPolicy: IfNotPresent`, installed
clusters froze on whatever `:main` image they first pulled and could not deterministically
receive shipped features (e.g. the model-config UI from the ISI-4822 epic). `v0.2.0`
makes "upgrade the cluster" a well-defined operation.

## What ships

- Git tag `v0.2.0` on `main` → `build-images.yml` publishes **semver-tagged** images
  (`type=semver,pattern={{version}}`) for the full component matrix at
  `ghcr.io/k8squad/ksquad-<component>:0.2.0`, plus cosign signatures + SLSA provenance.
- Control-plane chart (`config/helm`) `version`/`appVersion` → `0.2.0`. The default image
  tag falls back to `.Chart.AppVersion` (`_helpers.tpl`), so an unpinned install now
  resolves to `:0.2.0` images automatically.
- CRDs chart (`config/helm-crds`) `version`/`appVersion` → `0.2.0`, and the control-plane
  chart's `k8squad.io/min-crds-version` annotation → `0.2.0`. This is required: CRD schema
  additions since the freeze back the model-config UI — `ModelConfig` CRD + `Role` model
  tier (ISI-4459), `Role.activePhases[]` / `coordinatorMode` (ISI-4486), capability grant
  store on `Team` (ISI-4870), and more. CRD changes are additive-only, so newer CRD charts
  are always safe.

## Upgrade an installed cluster

CRDs first (ADR-0002, Option B — CRDs are a standalone chart, always upgrade before the
control plane):

```sh
helm repo add k8squad https://charts.k8squad.io && helm repo update
helm upgrade --install k8squad-crds k8squad/k8squad-crds --version 0.2.0
helm upgrade k8squad k8squad/k8squad --version 0.2.0
```

Pinning `--version 0.2.0` on the control-plane chart pins `appVersion 0.2.0`, which pins
the image tag to `:0.2.0` — immutable, so the rollout is deterministic regardless of the
`IfNotPresent` pull policy.

### If you are stuck on `:main`

A cluster that first pulled `:main` under `pullPolicy: IfNotPresent` will keep that cached
layer. Upgrading to the `0.2.0` chart changes the resolved tag to `:0.2.0`, which is a new
tag the node has never pulled — so the new image is fetched and the pods roll. No manual
`rollout restart` is normally required. If a Deployment was overridden to pin `:main`
explicitly (`controlPlane.image.tag: main`), clear that override so the tag falls back to
`appVersion`, then:

```sh
kubectl -n k8squad rollout restart deploy      # force re-pull of the resolved :0.2.0 tag
```

## Verify

After upgrade, the console shows the model-config surface:

- **Settings → Configuration → Model Priority**
- **Compose → Roles** model fields

## Out of scope

- Changing the default `pullPolicy` (kept `IfNotPresent`; pinning by immutable tag at
  install is the fix).
- `0.1.0` is **not** retagged/republished — the semver lane never fired for it, so it was
  never a real image tag. `0.2.0` is the first.
